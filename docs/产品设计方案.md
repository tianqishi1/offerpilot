# 求职 Agent 产品设计方案

产品代号：**OfferPilot · 职航**（暂定名）
版本：v0.1 ｜ 日期：2026-11-18 ｜ 前置文档：《求职Agent可行性调研报告.md》

> 设计前提（沿用调研结论）：做"人机协同、精投定制、本地优先"的求职 Copilot；
> 首发人群选定 **校招/应届生与实习生**（平台对抗最弱、痛点最集中、渠道可复制）；
> 架构预留社招与海外（Workday/Greenhouse/Lever）扩展能力。
> 明确不做：无人值守海投、集中代管账号、默认自动操作 Boss/LinkedIn 账号、编造简历内容。

---

## 1. 产品定位

**一句话**：面向应届生的 AI 求职副驾驶——让每一份网申只花 3 分钟，且每一份都是定制的。

- **价值主张**：不是帮你投得更多，而是帮你投得更准、填得更快、跟得更紧、准备得更充分。
- **北极星指标**：用户"投递 → 面试"转化率（行业基线 3.09%，定制简历基线 5.71%，目标 ≥ 6%）。
- **辅助指标**：单份网申耗时（30 分钟 → 3 分钟）、网申真实提交完成率 ≥ 98%。

**四条产品原则（写进团队共识）**
1. **人确认关键动作**：提交申请、发送消息、确认面试时间，永远由人点最后一下。
2. **质量优先于数量**：每日精推 3-5 个岗位，不做"一键投 100 家"。
3. **本地优先**：登录态留在用户浏览器；简历默认本地解析/加密存储；不集中爬取、不服务端代投。
4. **零编造**：所有简历内容可溯源到用户原始经历；AI 只做重组、润色、强调，新增内容必须标"待确认"。

**差异化（对比已有玩家）**
| 对比对象 | 他们的短板 | 我们的打法 |
|---|---|---|
| 海投机器人（LazyApply 等） | 停在草稿、封号、雇主反制 | 提交完成校验 + 精投定制，用面试率说话 |
| Simplify | 免费但自动提交弱、无结果闭环 | "真正能提交"的工程质量 + 结果数据飞轮 |
| 面灵/Offer快 | 核心押注 Boss 自动沟通，风控对抗强 | 主战场放企业官网/ATS 网申，对抗弱；Boss 模块后置且默认关闭 |
| 职芽 | 模拟面试强，网申填写弱 | 网申 autofill 为矛，面试准备为盾，漏斗全闭环 |

## 2. 目标用户与场景

### 2.1 用户分层
- **P0 校招/实习生**（本科/硕士应届，秋招春招）：网申表单繁琐、信息分散、简历不会定制、投后无反馈、面试焦虑。
- **P1 社招 1-3 年**（V1.2 后扩展）：复用同一引擎，换匹配策略与题库。
- **P2 海外/华人出海**（V2）：换 ATS 适配器（Workday/Greenhouse/Lever）与英文简历策略。

### 2.2 典型画像
**小林**，计算机硕士研二，秋招目标 30-50 家：
- 每份网申 20-40 分钟（注册账号、填教育/实习/项目、传附件、答开放题）；
- 岗位信息散落在官网、公众号、牛客、辅导员群；
- 一份简历投所有岗位，回复率 < 3%；
- 投完就忘，错过笔试/面试通知。

### 2.3 三个核心场景
1. **晚间集中网申**（高频，主战场）：打开 3-5 个目标公司官网 → 插件识别表单 → 一键定制简历 → 自动填写 → 预览确认 → 提交 → 自动记录。
2. **碎片时间看进展**（地铁/课间）：Web/手机看板 → 今日日报（新匹配、状态变化、截止提醒、跟进建议）。
3. **面试前突击**：公司/岗位题库 + 基于自己简历的预测问题 + 模拟面试与评估报告。

## 3. 产品形态与信息架构

### 3.1 形态选择：浏览器插件（主）+ Web 工作台（辅）
| 候选形态 | 结论 | 理由 |
|---|---|---|
| **Chrome/Edge 插件 + Web 工作台** | ✅ 首发 | 复用用户登录态与住宅 IP；能看到渲染后的 React 表单；风控对抗最弱；分发成本低；开发量最小 |
| 桌面客户端 | V2 再议 | 仅当 Boss 半自动模块/本地文件处理需求强烈时引入 |
| 纯 Web + 服务端代填 | ❌ 否决 | 机房 IP 被拦截、看不到渲染表单、集中代投法律风险最高（调研已验证） |
| 移动 App | 后置 | 网申必须在桌面浏览器完成；移动端只做看板/提醒（PWA 或小程序） |

### 3.2 信息架构
```
插件侧（Side Panel，随浏览器打开）
├─ 岗位卡片：当前页面岗位解析 → 匹配分/截止日/一键定制/收藏
├─ 网申助手：字段填写进度、置信度标色、待确认清单、提交预览
└─ 快捷动作：保存岗位、记录投递、生成跟进草稿

Web 工作台
├─ 今日求职（日报：精推 3-5 岗 + 管道变化 + 今日待办）
├─ 岗位库（聚合/收藏/匹配分排序/筛选）
├─ 我的画像（结构化简历、多版本管理、求职偏好）
├─ 投递管道（看板：待投→已投→笔试→面试→Offer→结束）
├─ 面试准备（题库/预测问题/模拟面试/评估报告）
└─ 设置（隐私与授权、数据导出/删除、通知、订阅）
```

## 4. 核心用户旅程

### 4.1 Onboarding（目标 < 5 分钟完成首次价值体验）
```
上传简历(PDF/Word/图片)
  → LLM 解析为结构化画像（置信度标注）
  → 用户确认/修正关键字段（学校/专业/毕业年份/实习/技能）
  → 设置偏好（城市/岗位方向/行业/公司类型/薪资底线）
  → 生成《求职策略卡》：竞争力评估 + 冲刺/匹配/保底三档建议
  → 立即推荐 3 个在招岗位（首次 aha：原来我的简历值这些岗位）
```

### 4.2 每日主循环（产品的心脏）
```
发现 → 评估 → 定制 → 填写 → 人确认 → 提交校验 → 追踪 → 准备 → 回流
```
1. **发现**：每日精推 3-5 个岗位（截止日临近优先），而非信息流轰炸。
2. **评估**：岗位适配报告 = 匹配分（分维度）+ 我的差距 + 简历调整建议 + 竞争/截止提示。
3. **定制**：一键生成定向简历 + 求职信/开放题答案，diff 预览，用户可编辑。
4. **填写**：在目标官网/ATS 页面唤起插件 → 自动填写 → 不确定字段高亮待确认。
5. **人确认**：提交前全量预览页，用户点"确认提交"（默认永不自动提交）。
6. **提交校验**：检测成功页/确认邮件/状态页，确认真正提交成功才记"已投递"；失败则重试或引导手动，绝不虚报。
7. **追踪**：管道自动/手动更新状态；截止、笔试、面试提醒；7 天无回复生成跟进草稿（人发送）。
8. **准备**：进入面试阶段自动推送公司题库 + 简历预测问题 + 模拟面试入口。
9. **回流**：用户标记结果（回复/面试/offer/挂），数据回流优化匹配与简历策略（飞轮）。

### 4.3 网申自动填写时序（核心工程流程）
```
用户打开申请页
 → 适配器识别（URL/DOM 指纹 → ATS 类型 + 版本）
 → 字段提取（渲染后 DOM + accessibility tree → 字段 schema）
 → LLM 生成 FillPlan JSON：{field, value, source, confidence}
    · 事实字段：只从用户画像取值（source=profile）
    · 开放题：LLM 基于画像生成（source=generated，标"待确认"）
    · 未知字段：留空标红（source=missing）
 → 执行填写（native setter + 合成事件；文件用 DataTransfer；
    combobox 走 search→select；多页表单走状态机逐页推进）
 → 侧栏显示进度与置信度标色（绿=确定 / 黄=待确认 / 红=缺失）
 → 用户处理黄/红字段 → 全量预览 → 用户点"确认提交"
 → 提交后校验（成功页特征/确认邮件/状态页）
 → 写入 Application 记录（含 FillPlan 快照，可审计可回放）
```

## 5. 功能模块设计

### M1 简历解析与用户画像
- **输入**：PDF/Word/图片（OCR）/手动填写；支持多份简历。
- **输出**：结构化 JSON（基本信息/教育/实习/项目/技能/获奖/求职意向），每字段带置信度与原文定位。
- **规则**：低置信度字段必须用户确认后才进入 FillPlan；敏感字段（身份证/手机号）默认仅本地存储。
- **交互**：解析结果卡片式确认，点击字段可看简历原文截图定位。
- **边界**：解析失败 → 引导手动模板；图片模糊 → 提示重传。

### M2 岗位聚合与匹配
- **数据源（合规优先级排序）**：
  1. 企业官网/ATS 公开职位页（用户浏览时插件端采集，结构化入库）；
  2. 精选校招聚合源（公开信息，标注来源与抓取时间）；
  3. 用户主动粘贴 JD / 导入链接；
  4. 合作渠道（高校就业网/企业，V1.2+）。
  - ❌ 不做：服务端集中爬取 Boss/LinkedIn、购买简历/职位数据。
- **匹配管线**：硬条件过滤（城市/学历/毕业年份/签证）→ 向量召回 → LLM 复核打分。
- **匹配分（0-100）分维度展示**：技能匹配 / 经历相关 / 竞争强度 / 时间窗口（截止日）。
- **岗位适配报告**：为什么推荐 / 我的差距（缺什么技能或经历）/ 简历调整建议 / 截止与流程提示。
- **去重与时效**：同一岗位多源去重；过期检测（页面 404/截止日/用户反馈）。

### M3 定向简历与求职信
- **流程**：JD 关键词抽取 → 简历条目重排/强调/润色 → ATS 关键词覆盖检查 → diff 预览 → 导出 PDF/Word。
- **事实护栏（硬规则）**：
  - 每条生成内容必须映射到原始简历条目（traceability id）；
  - 禁止新增经历/技能/数字；润色不得改变事实语义（如"参与"不得改成"负责"）；
  - 开放题答案中涉及事实的部分同样溯源；无法回答的标"需你补充"。
- **版本管理**：每个岗位一个简历版本，与 Application 绑定，可回溯"当时投的是哪版"。
- **求职信/开放题**：基于画像 + 公司公开信息生成，用户可编辑；提供 3 种语气（正式/真诚/简洁）。

### M4 网申自动填写（核心工程壁垒）
- **适配器层（Adapter Registry）**：
  - P0：北森、Moka（国内校招覆盖率最高的两个 ATS）+ 通用兜底适配器；
  - P1：牛客、智联校招、企业自建官网模板（Top 20 模板覆盖 ~80% 目标公司）；
  - P2（海外版）：Greenhouse、Lever、Workday、Ashby。
  - 每个适配器 = 字段 schema + 页面指纹 + 执行脚本 + 版本号；平台改版 → 指纹失配 → 自动降级通用适配器 + 告警。
- **通用兜底适配器**：LLM 直接读渲染 DOM 生成 FillPlan（慢但全覆盖），保证长尾表单"能填个八九成"。
- **已知坑与对策**（调研已验证的公开解法）：
  | 坑 | 对策 |
  |---|---|
  | React 受控组件不认 value 赋值 | native setter + input/change 合成事件 |
  | 文件上传 input 无法直接赋值 | DataTransfer API 构造 FileList |
  | React Select/combobox | 模拟 search → 等待选项 → select |
  | Workday 私有组件 | 专用适配器 + 键盘事件序列 |
  | 多页表单 | 状态机逐页推进，每页独立 FillPlan |
  | CSRF token 导致缓存失效 | 缓存 key 剔除动态 token；按 ATS+模板版本缓存 |
- **提交校验（反"草稿幻觉"）**：成功页特征匹配 / 确认邮件检测（用户授权后）/ ATS 状态页回查；三选一通过才记"已投递"，否则记"待验证"并提醒用户。
- **审计**：每次填写保存 FillPlan 快照 + 页面截图（本地），可回放、可申诉、可调试。

### M5 投递管道与跟进
- **看板状态机**：
  `待评估 → 待投递 → 已填写 → 已确认 → 已提交(已验证) → 筛选中 → 笔试 → 面试 → Offer → 结束(拒绝/放弃/无响应)`
- **状态更新**：插件检测 ATS 状态页（用户打开时）> 用户手动 > 邮件解析（V1.1，需单独授权，默认关闭）。
- **提醒**：申请截止（前 3 天/前 1 天）、笔试/面试日程、7 天无回复跟进建议。
- **跟进**：生成跟进邮件/消息草稿 → 用户一键复制发送（不代发）；跟进模板按场景（网申后/面试后/offer 谈判）。
- **周报/日报**：本周投递数、面试转化率、管道健康度、下一步建议（精投策略而非加量）。

### M6 面试准备
- **题库**：公司×岗位维度（公开面经结构化 + 用户回流沉淀，标注来源）；校招垂直题库是长期壁垒。
- **简历预测问题**：LLM 基于"这份简历 + 这个 JD"预测面试官最可能追问的 10 个问题（含项目深挖）。
- **模拟面试**：文字/语音（V1.2），AI 追问，结束后评估报告（结构化表达/技术深度/与 JD 差距/改进建议）。
- **Offer 对比**：薪资/城市/成长性/户口档案等多维打分（校招特有维度）。

### M7 Boss 半自动沟通（V2 可选模块，默认关闭）
- 前提：用户显式授权 + 风险告知书签署；桌面客户端形态。
- 硬限制：每日上限（≤30）、随机间隔、话术逐条个性化、受限即熔断、每条消息发送前预览确认（或批量预览后逐条放行）。
- 定位：辅助而非核心；任何封号投诉触发该模块全局下线评估。

## 6. 关键交互设计

### 6.1 插件侧栏（网申场景）
```
┌─────────────────────────────┐
│ ● OfferPilot   北森·已识别   │
├─────────────────────────────┤
│ 匹配分 86  截止 11-25 ⚠     │
│ [一键定制简历]  [查看适配报告]│
├─────────────────────────────┤
│ 填写进度 18/21               │
│ 🟢 教育经历(4)  🟢 实习(6)   │
│ 🟡 开放题"为什么选我们"(2)   │
│ 🔴 期望薪资(1) ← 需你填写    │
├─────────────────────────────┤
│ [预览全部答案]               │
│ [确认提交] ← 永远人工点击    │
└─────────────────────────────┘
```
- 置信度标色：绿=画像直取，黄=AI 生成待确认，红=缺失必填。
- 黄/红字段点击 → 展开编辑框 + 来源说明（"来自你简历第 2 段实习" / "AI 生成，请核实"）。
- 提交按钮旁永远显示"提交后将校验是否真正送达"。

### 6.2 Web 今日求职（日报）
```
┌──────────────────────────────────────────┐
│ 早上好，小林。今天建议投这 3 个：          │
│ 1. 字节·后端(匹配92, 截止3天) [定制并填写] │
│ 2. 美团·平台(匹配88, 截止7天) [定制并填写] │
│ 3. 蚂蚁·数据(匹配85, 新发布)  [查看报告]   │
├──────────────────────────────────────────┤
│ 管道变化：华为 简历过筛→笔试(11-22) ⏰     │
│ 跟进建议：蔚来 7天未回复 [生成跟进草稿]    │
│ 本周：投 9 / 面试 2 / 转化率 22% ↑        │
└──────────────────────────────────────────┘
```

### 6.3 文案与信任原则
- 不贩卖焦虑、不承诺"保 offer"；所有 AI 生成内容显式标注。
- 每个自动动作可审计、可撤销、可回放；隐私设置一键导出/删除全部数据。
- 失败诚实：填不了就说填不了，降级手动引导，绝不虚报"已投递"。

## 7. 技术架构

### 7.1 总体
```
┌─ 用户浏览器 ────────────────────────────────┐
│ Chrome/Edge 插件 (MV3)                      │
│  ├ content script：DOM提取/填表执行/页面指纹 │
│  ├ side panel：岗位卡片/填写进度/提交预览    │
│  ├ background：适配器调度/状态机/本地缓存    │
│  └ IndexedDB：画像/简历/FillPlan快照(加密)   │
│        │ 仅上传：脱敏画像+JD+生成请求        │
└────────┼────────────────────────────────────┘
         ▼
┌─ 云端 ──────────────────────────────────────┐
│ API 网关 / 认证 /  consent 管理              │
│  ├ 画像服务：解析(小模型)+结构化校验         │
│  ├ 匹配服务：硬过滤→向量召回→LLM复核打分     │
│  ├ 生成服务：定向简历/求职信/开放题/面试题   │
│  │   (大模型 + JSON Schema 约束 + 事实护栏)  │
│  ├ 适配器注册中心：schema/指纹/版本/灰度     │
│  └ 漏斗遥测：投递→回复→面试→offer(匿名化)   │
│ 向量库(岗位/简历) ｜ 对象存储(导出件)        │
└─────────────────────────────────────────────┘
```

### 7.2 关键决策
- **登录态不出浏览器**：插件复用用户 cookie，云端永不持有平台凭证。
- **简历最小上传**：默认本地解析（端侧小模型/规则），云端仅接收脱敏结构化画像用于匹配与生成；用户可选"云端增强解析"（单独同意）。
- **LLM 分层控成本**：抽取/分类/字段映射用小模型；简历生成/匹配复核/模拟面试用大模型；结构化输出统一 JSON Schema + 校验重试。
- **国内合规默认**：默认国内 LLM API（数据不出境）；海外版单独部署与同意流程。
- **适配器热更新**：注册中心下发 schema/脚本版本，平台改版无需发版即可修复；失配自动降级通用适配器。
- **评测体系（上线门槛）**：
  - 填表字段准确率 ≥ 95%（标注集：Top 20 表单 × 50 字段）；
  - 简历事实性错误率 < 1%（溯源校验 + 人工抽检）；
  - 提交完成率 ≥ 98%（含校验）；
  - 匹配质量：内测用户"推荐采纳率"与 NDCG 离线评测。

### 7.3 成本估算（单用户/月）
- LLM：解析+匹配+生成+面试 ≈ ¥5-20（分层模型 + 缓存后）；
- 向量/存储/带宽 ≈ ¥1-3；
- 对照定价 ¥69/月，毛利空间充足；免费层用限额控制成本。

## 8. 数据模型（核心实体）

```
UserProfile      画像：结构化简历字段 + 偏好 + 置信度
Resume           原始简历文件(本地/加密) + 解析结果 + 版本
Job              岗位：来源/JD结构化/截止日/指纹/时效状态
JobMatch         匹配：分数(分维度)/差距/建议/解释
Application      投递：job_id + resume_version + 状态机 + 时间戳
FillPlan         填写计划：field/value/source/confidence + 页面快照
Adapter          适配器：ATS类型/版本/字段schema/执行脚本/指纹
FollowUp         跟进：草稿/发送记录(用户手动)/结果
Interview        面试：日程/题库/模拟记录/评估报告
OutcomeEvent     结果回流：回复/笔试/面试/offer/拒绝(匿名化遥测)
Consent          授权：分项同意记录(解析/邮件/遥测/Boss模块)
```

**Application 状态机**（与 M5 一致）：
`draft → filled → confirmed → submitted → verified → screening → test → interview → offer → closed(rejected/withdrawn/ghosted)`
- 只有 `verified` 才计入"有效投递"统计；`submitted 未 verified` 单独提示。

## 9. 安全、合规与风控设计

| 层面 | 设计 |
|---|---|
| PIPL | 分项单独同意（解析/云端增强/邮件/遥测/Boss）；最小必要；默认本地+加密；一键导出/删除；不转售、不共享给第三方 |
| 数据出境 | 国内版默认国内 LLM；海外版独立部署与同意 |
| 平台规则 | 不集中爬取、不服务端代投、不默认操作 Boss/LinkedIn；用户自有账号+住宅 IP；所有平台内动作限速+熔断 |
| 反幻觉 | 事实字段仅取画像；生成内容溯源 id + 显式标注；knockout 问题（学历/签证/竞业）一律用户自答 |
| 提交真实性 | 三重校验（成功页/邮件/状态页），杜绝"草稿幻觉" |
| 审计 | FillPlan 快照 + 动作日志本地留存，可回放可申诉 |
| 未成年人/敏感信息 | 身份证等敏感字段默认不出本地；日志脱敏 |
| 账号风险告知 | 涉及平台内操作前展示风险告知书；封号投诉 = 0 为护栏指标 |

### V1.2（+6 周）
结果数据飞轮上线（匹配校准+简历策略 A/B）、模拟面试（文字→语音）、Offer 对比、高校渠道版（B2B2C）。

### V2（视数据决策）
Boss 半自动可选模块（桌面客户端）、海外版（Greenhouse/Lever/Workday + 英文简历）、社招扩展。

## 附录 B：北森 vs Moka 适配器对比（2026-11-18 补充调研）

> 结论先行：两者不是"同一件事的两套皮肤"。客户覆盖、门户架构、集成路径、表单标准化程度、工程量都不同。
> **建议把 MVP 顺序调整为 Moka 先（W1-2）、北森后（W3-4）**，理由见下。

### B.1 平台事实对比

| 维度 | 北森（iTalentX 招聘云） | Moka（智能化招聘 ATS） |
|---|---|---|
| 产品定位 | 一体化 HR SaaS（招聘/测评/绩效/人事全模块），招聘是其中之一 | 新生代招聘 ATS 起家（后扩展 Moka People 人事），招聘体验是核心卖点 |
| 候选人门户 | **每租户独立子域** `*.zhiye.com`（如 foresealife.zhiye.com/campus），含个人中心/投递记录页 | **统一域名** `app.mokahr.com` + 组织路径（社招/校招分路径），门户标准化 |
| 典型客户 | 大中型企业/国企/金融/制造校招为主（上海银行万人 AI 面试案例；6000+ 企业；13 行业校招方案） | 互联网/新经济为主（小米、360、滴滴、bilibili、欢聚等 700+ 校招客户） |
| 门户标准化 | **"多样式网申门户"+支持换肤/定制**，企业自定义字段、附件、内推码常见 → 租户间差异大 | 标准化 SaaS 产品，租户间表单结构高度一致 → 一套适配器覆盖多数租户 |
| 开放接口 | 无公开候选人侧 API；iTalentX 开放平台需**企业侧授权** | **有官方开放 API**（api.mokahr.com，文档明示"获取招聘官网职位信息 + 投递简历到职位"）；另有开放平台 accessToken/clientSecret 体系（企业侧）；社区已有 Moka MCP server（GET /jobs/{orgId}，social/campus）与第三方职位数据源 |
| 简历解析 | 有解析能力，但网申以**多段表单填写**为主 | **解析是强项**（20+ 格式/OCR/宣称 98% 准确率），投递流程常为"上传简历→自动解析→确认补全" |
| 典型投递流程 | 注册(手机验证码)→多段表单(基本/教育/实习/项目/附件/开放题/内推码)→**测评/AI 面试(独立链接、监考防作弊)**→面试→Offer/三方 | 上传简历→解析确认→补全字段→提交；候选人状态页统一 |
| 状态追踪 | zhiye.com 个人中心投递记录（租户子域内） | mokahr 候选人状态页（统一域名，易适配） |

### B.2 适配器工程策略差异

| 工程点 | 北森适配器 | Moka 适配器 |
|---|---|---|
| 集成路径 | **DOM-first**：无公开 API，只能在用户浏览器内做 | **API-first（聚合）+ DOM（投递）**：职位聚合可走官方接口/公开页，合规友好；投递接口是否候选人侧可直接调用需实测（鉴权多为企业侧授权） |
| 核心策略 | 逐字段填写：字段提取→FillPlan→native setter 回填 | **可走"上传定制简历→平台自解析→校验补全"主路径**：我们的定向简历 PDF 即输入，平台解析后只核对/补少量字段 → 字段级工程量小、天然绕开 React 受控组件坑 |
| 适配器形态 | **适配器族**：zhiye.com 基础适配器 + 租户 schema 覆盖表（子域指纹→字段映射）+ 通用兜底 | **单一适配器** + 版本管理（统一域名/统一组件），维护成本低 |
| 主要坑 | 租户定制组件、附件上传、多步表单、内推码/自定义必填项、门户换肤导致指纹漂移 | 解析结果字段映射核对、combobox、文件上传；API 版本切换（官方文档有新老版本） |
| 工程量估计 | 重（约 2-3 周含租户覆盖表） | 轻（约 1-1.5 周，解析辅助路径更短） |
| 覆盖价值 | 传统大厂/国企/金融校招（Moka 覆盖不到的雇主人群） | 互联网/新经济校招（我们 P0 计算机应届生的主目标群） |

### B.3 共同点（不变的核心）
- 都复用**同一套 FillPlan / 置信度标色 / 人工确认 / 提交校验 / 审计快照**内核；适配器只是"字段 schema + 执行脚本"层。
- 注册/手机验证码环节**永远人工**；**测评/笔试/AI 面试绝不自动化**（监考防作弊，伦理与合规红线，两平台同理）。
- 都是雇主自有 ATS（非 Boss/LinkedIn 类平台），用户自有账号+住宅 IP 操作，风控对抗性低。
- 都是多租户 SaaS 集中升级：需要指纹版本监测 + 热更新 + 失配降级通用适配器。

### B.4 对 MVP 排期的调整建议
- 原排期 W1-2 北森 / W3-4 Moka → **建议对调：W1-2 Moka（轻、快、互联网校招主目标、解析辅助路径）/ W3-4 北森（重、租户覆盖表、传统大厂校招）**。
- 第 14 节"抽样 20 家目标公司官网"仍需执行：统计 zhiye.com / mokahr / 自建占比，用数据最终确认顺序与适配器族规模。
- 竞争提示：校招网申 autofill 已有玩家（智简网申助手、求职喵插件等），验证了需求与可行性，也说明"提交校验 + 定制简历 + 结果闭环"才是差异点，纯填表无壁垒。

## 附录 C：20 家目标公司 ATS 抽样调研 + API 获取模型核实（2026-11-18）

> 本附录回答两个问题：① 首发适配器到底该选谁（抽样 20 家校招目标公司）；② Moka/飞书/北森的 API 是否需要"订阅"。
> **两个结论都修正了前文假设**：抽样推翻了"北森+Moka 为 P0"；API 核实推翻了附录 B"Moka 聚合可走官方 API"的说法。

### C.1 API 获取模型核实（回答"要不要订阅 API"）

**结论：不需要订阅，而且作为求职者侧工具也"订阅不到"。三家 ATS 的开放接口都是企业侧授权，不是公开开发者订阅服务。**

| 平台 | 接口 | 鉴权模型 | 我们能否直接用 |
|---|---|---|---|
| Moka | 官方开放 API（api.mokahr.com，v1/v2/candidate 三套路径；含"获取官网职位+投递简历"接口） | **clientId/clientSecret 或 API Key 由 Moka CSM（客户成功经理）发放给雇主企业**，Basic Auth；社区 Moka MCP server 实测同样必须填 MOKA_API_KEY（CSM 发放）+ MOKA_ORG_ID | ❌ 不能公开订阅。合法路径=逐个雇主授权（不现实）/ B2B2C 合作 / 成为 Moka 生态供应商 |
| 飞书招聘 | open.feishu.cn Hire v1 API | tenant_access_token，需**企业自建应用或 ISV 应用+雇主授权**，权限逐项审批 | ❌ 同上，企业侧授权 |
| 北森 | iTalentX 开放平台 | 企业侧授权，无公开候选人侧 API | ❌ |

**因此 MVP 聚合不依赖任何付费/授权 API，替代路径（按合规优先级）：**
1. **用户端插件采集（主路径）**：用户自己浏览招聘官网时，插件在用户浏览器内结构化采集职位——等价于用户浏览行为，最合规，且天然拿到渲染后数据。
2. **招聘官网公开页/公开前端接口**：在用户浏览器内低频访问（与页面同源），非官方开放能力，需限速+变更监测+合规评估。
3. **公开聚合源**：牛客企业页、应届生求职网、高校就业网公告（标注来源与时间，做去重与时效校验）。
4. **可选付费第三方数据**（如 jobo.world 的 Moka ATS 数据订阅）：MVP 不需要；规模化后可评估，注意数据许可与新鲜度。

**唯一持续成本 = LLM 调用（已预算 ¥5-20/用户/月）+ 可选数据源。"订阅 API"不是必需成本项。**

> ⚠️ 对附录 B 的修正：B.2 中"Moka 聚合走 API-first（官方接口）"表述不准确。官方接口需企业授权，候选人侧不可得。
> 修正为：**聚合以用户端采集为主、公开页为辅**；Moka 适配器的价值在"投递端标准化 + 上传简历借平台解析"，不在官方 API。

### C.4 统计与关键发现

**门户类型分布（20 家）：**
| 类型 | 数量 | 占比 | 公司 |
|---|---|---|---|
| 自研/轻量自研 | 14 | 70% | 字节/腾讯/阿里/美团/百度/京东/网易/快手/华为/蚂蚁/拼多多/小红书/招行/DeepSeek |
| 飞书招聘 | 2 | 10% | 小米（私有化域名）/智谱 |
| Moka（确证） | 1 | 5% | 月之暗面 |
| 自定义域名·疑似 Moka·待实测 | 2 | 10% | B站/米哈游 |
| 自研/其他·待实测 | 1 | 5% | 滴滴 |
| **北森** | **0** | **0%** | —（北森样本集中在制造/国企/金融：三一/厦门国际银行/上海银行） |

**发现 1：对 P0 人群（计算机应届→互联网/AI），自研门户是绝对主流（70%+），北森为 0。**
→ 原设计"北森+Moka 为 P0 适配器"的假设被抽样推翻。**真正的 P0 是通用 LLM-DOM 适配器**（覆盖自研长尾），而非任何单一厂商适配器。

**发现 2：ATS 厂商 ≠ 网申门户。**
小米/滴滴/B站都在 Moka 客户名单里，但候选人实际填表的门户分别是飞书私有化域名/自研 Portal/自定义域名。
→ 适配器必须按**门户域名+DOM 指纹**选型，不能按厂商客户名单选型；厂商案例只能作旁证。

**发现 3：迁移与双轨真实存在。**
小米（Moka 案例→飞书门户）、月之暗面（Moka 投递短链 + 飞书内推页并存）。
→ 指纹注册中心必须带版本监测+迁移告警+热更新；同一公司可能多门户并存（快手信息/投递双域名、网易互娱/雷火独立站）。

**发现 4：Moka/飞书门户高度标准化，单适配器覆盖面大。**
- Moka：`app.mokahr.com/campus-recruitment/{org}/{id}`（含 app-tc 变体、/su/ 短链、channelToken 参数、自定义域名）。
- 飞书：`{org}.jobs.feishu.cn`（含私有化 `jobs.f.{企业域名}`，如小米 mioffice.cn）。
→ 这两个适配器 ROI 高（一套覆盖大量 AI 创业/新经济/消费/商管雇主），但优先级排在通用适配器之后。

**发现 5：雇主侧也在上 Agent。**
美团校招官网已内置"校园招聘Agent"（浙大就业网公告提及）。
→ "agent 对 agent"的交互未来可能出现；我们的差异化仍在候选人侧全漏斗（定制/填写/追踪/准备/结果闭环），而非单点填表。

### C.5 修正后的适配器优先级与 MVP 排期

| 优先级 | 适配器 | 覆盖 | 理由 |
|---|---|---|---|
| **P0** | **通用 LLM-DOM 适配器** + 1-2 个自研标杆打磨（建议百度 talent.baidu.com / 美团 zhaopin.meituan.com，表单规范、流量大） | 70%+ 自研门户 | 抽样证明这才是主战场 |
| **P1** | 飞书 `{org}.jobs.feishu.cn`（含私有化域名）+ Moka `app.mokahr.com`（含短链/自定义域名/channelToken 指纹） | AI 创业/新经济/消费/商管 | 高度标准化，一套覆盖多租户；Moka 可借"上传简历→平台解析"路径 |
| **P2** | 北森适配器族（zhiye.com 子域+租户 schema 覆盖表） | 制造/国企/金融/传统行业校招 | P0 人群中占比为 0；待用户群扩展后再投入 |

**MVP 排期修正（替代第 10 节 W1-4 安排）：**
- W1-2：通用 LLM-DOM 适配器 + 百度/美团标杆全链路（FillPlan/置信度/人工确认/提交校验/审计）。
- W3-4：飞书 jobs.feishu.cn 适配器 + Moka app.mokahr.com 适配器 + 指纹注册中心 v1（含迁移监测）。
- 北森适配器族移至 V1.1+，视用户群扩展决策。
- 待实测项（内测期用插件抓页面指纹确认）：B站、米哈游、滴滴底层厂商；DeepSeek 投递机制。
